# The Bootstrap Project: Rules and Plan

## 1. Purpose and status of this document

Build an understandable, hand-entered chain of tools, beginning with an assembler written in GW-BASIC and eventually reaching a self-hosted compiler, supporting utilities, a linker, libraries, and a small operating system.

Learning and independent construction are central goals. The reader should understand what they type, be able to test it in manageable stages, and retain a working tool at each major milestone. Short articles, modest typing requirements, and gradual progress are primary design concerns: a human will enter every required line.

This is a fresh start. Use this document and decisions made for this version of the project; do not use previous conversations to guide development.

Publish the articles as static HTML generated by Hugo. Keep all intermediate builds and source files in a directory named `pub_src`. Publish the generated website to `public` at the project root.

This file is the project plan, not a magazine article. It may discuss sequencing, future work, production procedures, and unresolved decisions. The articles themselves must follow the stricter editorial rules below.

### Bootstrap ladder

| Stage | Tool | Purpose and implementation |
|---|---|---|
| 1 | BOOTASM | An assembler written in GW-BASIC; the starting point for the toolchain. |
| 2 | ASM86 | An assembler written in assembly accepted by BOOTASM. It self-assembles and builds the first ASM86A seed. |
| 3 | ASM86A | A larger assembler constructed in ASM86 through a small streaming seed, then self-assembled. Stream input and output, allocate substantial symbol storage, and provide the addressing/instruction support needed by larger tools. |
| 4 | IR86 | A processor-independent intermediate language and translator. The expanded implementation is built with ASM86A and emits ASM86A-compatible 8086/8088 assembly. |
| 5 | RILL | A language with Rust-like syntax, without a commitment to Rust's full safety checking or other features. Its initial compiler is written in IR86; expand it using the capacity supplied by ASM86A and the expanded IR86. |
| 6 | Rebuild in RILL | Reimplement the assemblers and later tools in RILL, working toward a self-hosted toolchain. |

Later work will cover a linker, libraries, larger programs, expanded language and assembler features, and a small operating system. Detailed scope and ordering remain to be decided.

The complete toolchain is implemented and verified. Unchanged ASM86 builds ASMA0, which builds ASM86A. The streaming native IR86 bridge builds the IR-written compiler seed; that compiler builds RILL implementations of the compiler (26625 bytes), IR86 (31472 bytes), and ASM86A (32404 bytes). Both rebuild generations reproduce all three tools using only the RILL-written trio. The initial smaller constructions in sections 11 and 12 remain explicit, separately named bootstrap milestones. See [TOOLCHAIN_Design.md](TOOLCHAIN_Design.md).

## 2. Non-negotiable editorial rules

- Write as an original hands-on programming magazine series with a **1986 technical horizon**, in the spirit of Dr. Dobb's Journal. Do not claim affiliation or pretend the articles are authentic historical publications.
- Present each collection as its first publication. Do not discuss revisions, previous drafts, AI-generated development, editorial corrections, or abandoned approaches in article prose.
- Acknowledge the BASIC series as the foundation of the assembly series. A brief prerequisite reference to an earlier published collection is appropriate; revision-history commentary is not.
- Keep article explanations self-contained. **Only introductions may acknowledge future goals.** The body should explain the program being constructed, without promises about a later compiler, operating system, or installment.
- Do not use checksums. Do not mention checksums or checksumming in articles, listing commentary, or reader-facing companion documentation.
- Do not mention modern development machinery in reader-facing material: Unicorn, Python harnesses, automated regression infrastructure, modern build verification, AI tools, or similar production details.
- Do not insert web addresses, online archives, or digital-transcription references into the period magazine narrative. Cite appropriate printed manuals by title, publisher, date, and relevant section when needed.
- Do not replace modern testing disclosures with invented claims of testing on period hardware. Give the reader reproducible DOS/GW-BASIC checks and expected results.
- Use clear, patient language suitable for a beginner. Explain unfamiliar terms where they are used.
- Do not announce how many source lines a listing, patch, or completed checkpoint contains in published prose. Keep typing-size budgets as internal authoring constraints. Retain line numbers needed to locate edits and source limits needed to explain program behavior.
- Keep real limitations explicit. Distinguish CPU capabilities from the smaller language our assembler accepts. Do not imply support for full C merely because the assembler can support a small compiler.
- Explain all limitations fully, including why each limitation was chosen.
- Use natural, concrete prose consistent with the 1986 setting. Avoid formulaic or AI-sounding language.
- Double-check all produced text and code for correctness.

## 5. Code and type-in rules

### Size and readability

- Keep articles and required type-in code short. Include the explanation needed for understanding, but defer features that would make a step too large.
- Build BOOTASM in logical, testable chunks of **no more than 50 required BASIC source lines per chunk**.
- Assembly sections may exceed 50 lines. Keep them as small as practical; organize by a coherent routine or capability rather than an arbitrary page break.
- Treat line counts as a ceiling, not a target. Do not pack long statements or several unrelated operations onto a line merely to meet the limit.
- Favor beginner-readable code while economizing on lines people must type. Avoid unnecessary scaffolding, repetitive instructions, and needless register reloads.
- Silently apply straightforward instruction economy. Do not add prose congratulating the implementation for eliminating redundant reloads.
- Do not trade understandable control flow for obscure tricks simply to save a few lines.
- There is no fixed limit on convenience features. Include them only when their benefit justifies the added typing, explanation, and implementation complexity.

### Gradual progression

- Add one small, coherent capability at a time, with a working and visibly testable stopping point before the next addition.
- Introduce prerequisites before relying on them. Do not make large jumps merely to reach the next named tool sooner.
- Spread each tool's construction across as many installments and checkpoints as needed. The tool sequence describes milestones, not the size of individual steps.
- Account for the reader's total typing burden, including source changes, replacement blocks, helpers, and test input. Avoid repeated retyping of large sections.
- If a proposed step's size or conceptual jump is uncertain, ask the user about pacing before committing to it.

### Bootstrap integrity

- Every stage must be buildable with a tool the reader already has.
- Start with GW-BASIC and the DOS workbench, then build each tool using the preceding tools in this project. No outside assembler, compiler, linker, code generator, or prebuilt project executable may supply any part of the bootstrap chain.
- Keep IR language semantics independent of CPU and OS conventions; put those conventions in the backend and runtime binding.
- Build the first ASM86 executable with BOOTASM. Build ASMA0 directly with the unchanged ASM86, then ASM86A with ASMA0. Build the expanded IR86 with ASM86A, and RILL with IR86 and ASM86A. Preserve the existing baseline chain while constructing the inserted stage.
- Target DOS `.COM` executables only for now. Keep near code, ordinary data, and stack in the main segment; permit explicitly DOS-allocated auxiliary workspace selected through ES for larger tools. This workspace does not expand a `.COM` file's near-code/image limit or introduce an `.EXE` format. Defer multisegment code, linking, and other executable formats.
- Fixed input/output filenames are acceptable for early tools. Use COPY to select source files; filename prompts and command-line parsing are not prerequisites. Expanded tools should stream files through bounded blocks rather than buffer their complete input or output.
- Clearly distinguish the language used to **implement** an assembler from the assembly language it **accepts** and the machine code it **emits**.
- Do not silently use a new instruction in the assembler's own source before the preceding assembler can assemble it.
- Preserve a known working bootstrap executable under a separate name.
- Keep symbol-table bounds, source limits, memory use, stack requirements, and short-branch reach explicit.
- Do not quietly adopt 80186/286/386 instructions merely because the user's emulated machine can execute them. The established instruction baseline is 8086/8088.

### Listing presentation

- Show exact insertion points, enough surrounding code to locate them, and complete replacement blocks. Avoid vague directions such as “change the parser accordingly.”
- Make it unambiguous whether a block is new source, replacement source, a command, or an example.
- Printed margin numbers must be clearly separate from actual source. BASIC line numbers are source and must be typed.
- Explain inputs, outputs, scratch variables or registers, preserved state, and important side effects for each substantial routine.
- Explain data representation, instruction encoding, and branch calculations alongside the relevant addition.
- Preserve ASCII source, DOS-compatible line endings, and practical 8.3 source filenames for the period workbench.

## 6. Required structure of an installment

Each construction installment must contain:

1. A concrete objective and a short explanation of the problem it solves.
2. An explanation of why this part is needed at this point in the construction, grounded in the current program and its prerequisites.
3. The necessary concepts, introduced at the point of use.
4. Exact source additions and replacements.
5. Detailed explanations of each addition, including interactions with existing routines.
6. A stopping point that can be assembled or run with tools already available.
7. Exact test input, commands, and expected output or machine bytes, following the checkpoint rules below.
8. At least one relevant rejection or boundary case when the new behavior warrants it.
9. Brief troubleshooting advice tied to likely mistakes.

### Checkpoint rules

- Every checkpoint must give the reader a visible result wherever practical: console text, a displayed value, or a named output file with exact inspection instructions and expected contents.
- If a test communicates only through DOS exit status, print a small batch check that reports both PASS and FAIL; do not treat a silent return to the prompt as evidence of success. Check the status immediately, before launching any other program.
- Expected rejection tests must visibly distinguish the expected failure from unexpected acceptance. State the exact diagnostic or status and how to observe it.
- Binary viewers must display the file length as well as bytes, so a valid empty output is visibly distinguishable from no result.
- Never execute a fixture intended only to test instruction encoding; inspect its emitted bytes instead.
- Prefer existing console reports, `TYPE`, a small `VIEW.BAS`-style viewer, or a shared `CHECK.BAT` helper over adding substantial test machinery to the compiler itself.

## 9. Publication hierarchy and BOOTASM scope

The overall Bootstrap Experiment introduction is the parent of the tool collections. BOOTASM and ASM86 are siblings; each tool's installments belong beneath its own collection. BOOTASM construction precedes ASM86 construction; both collections are now authorized.

The first BOOTASM collection contains a workbench guide, eighteen construction installments, a complete language reference, and three complete example programs. The BASIC construction begins with a one-byte disk exercise, then grows through seventeen assembler checkpoints.

The initial assembler produces DOS `.COM` images of at most 4,096 bytes. It supports byte and word data, unsigned decimal and hexadecimal values, two-pass labels, selected register operations, direct and BX-based memory transfers, near calls and jumps, and short conditional branches. Keep the exact accepted forms and resource limits in its published reference. Its purpose is to provide a small working assembler and the starting vocabulary for ASM86; expanded instruction and addressing support must be introduced gradually when needed.

Keep publication sources in `pub_src/site`, period workbench sources in `pub_src/workbench/bootasm`, and generated HTML in `public` at the project root. Keep production procedures and verification records separate from the reader-facing articles, under `pub_src/tools` and `pub_src/qa`.

## 10. ASM86 construction scope

ASM86 begins with a short DOS message program, then adds decimal reporting, errors, filename input, file handles, byte reading, physical lines, tokens, lookup tables, values, output buffering, data directives, two passes, registers, labels, and instruction families. Twenty-nine buildable source checkpoints precede a thirtieth installment that compares two native self-assembly generations with the BASIC-produced original. A workbench guide, a complete reference, and three short executable examples accompany them. Keep new collection artwork distinct from BOOTASM's.

The completed BOOTASM.BAS must directly assemble every ASM86 construction source, including the final native assembler, without a preparatory patch or alternate assembler variant. Give BOOTASM a 256-entry symbol table, a 4,096-byte output limit, and a 2,000-line source limit; all ASM86 construction sources must fit those bounds and use only its accepted instructions. The final native image is 2,622 bytes. Keep each assembly addition coherent and modest enough to type. Printed edits identify exact old context and are applied from the bottom upward to preserve physical line locators.

The native accepted instruction forms remain the small BOOTASM subset, with token boundaries made explicit. ASM86's limits are 8,192 output bytes, 4,000 source lines, 120 physical characters per line, sixteen-character tokens/names, and 256 symbols. It uses DOS handle services, buffers output until two passes succeed, returns a DOS status, and requires a full 64 KB segment with entry SP=FFFEH. Fixed memory locations, routine interfaces, exact encodings, limitations, and error codes belong in the reference. This language is the initial target contract for IR86; it does not imply a complete Intel assembler.

Keep ASM86 workbench sources in `pub_src/workbench/asm86`, source downloads beneath `pub_src/site/static/downloads/asm86`, and verification evidence in `pub_src/qa/asm86`. Source archives contain no prebuilt executable or historical interpreter. Production scripts may prepare and verify manuscript/source text; they must not translate assembly into machine code. Reader executable bytes must come from executing the published BASIC or native assemblers.

## 11. IR86 language, backend, and runtime

IR86 is a processor-independent virtual machine with an accumulator A, explicitly defined sixteen-bit word semantics, an abstract expression stack, and byte-addressed declared storage. Its language must not expose physical registers, processor flags, segments, interrupts, operating-system service numbers, or native descriptor values. Fixed value widths and canonical low-byte-first word storage are IR semantics, not requirements for a particular CPU. Portable pointers come from ADDR; portable handles come from file services and remain opaque.

A backend implements the language, and an environment binding implements byte streams and files. The current backend and binding are written in assembly accepted by the completed ASM86 and emit ASM86-compatible source. Keep BOOTASM and ASM86 unchanged as preceding tools. The native translator is 6,407 bytes and directly fits ASM86. Test the complete BOOTASM → ASM86 → IR86 → assembly → executable chain without prebuilt project executables.

The portable runtime API consists of STATUS, PUTC, GETC, OPEN, CREATE, READ, WRITE, and CLOSE. Services update a persistent status word: zero for success, one for failure. STATUS reads that word; ordinary computations do not replace it. GETC distinguishes every byte from EOF (65535). OPEN/CREATE return opaque readable/writable handles. READ/WRITE consume a saved handle and buffer pointer with the count in A, return actual progress, and leave an empty expression stack. Normalize OS errors, permissions, partial writes, zero-count behavior, and handle lifetime inside the binding.

Reuse the published AS07 reader as the initial construction base. Supply thirty-two gradual checkpoints, a complete pipeline exercise, the language and separate target-profile reference, portable console/stream examples, and a file copier. Preserve established article filenames. Present the language as its first publication; explain assembly details as backend implementation choices. Do not announce listing or patch line totals.

The current source format has fourteen-character names, sixteen-character tokens, unsigned numeric spelling, and BYTE/WORD/BUFFER declarations. Arithmetic and bit operations have fixed word results; comparisons explicitly select signed or unsigned order. Calls pass and return A with empty expression temporaries. There is no automatic frame, memory safety, multiply/divide, floating point, or physical-register escape. The current compiler checks at most thirty-two saved expression words per basic block.

The 8086/DOS profile uses U_ program names, I_ entry/skip names, and R_ runtime names. Its selected runtime reserves 448 machine bytes and 42 definitions. Count these against the 8,192-byte image and 256-definition limits, along with the entry header. Generated text is limited to 32,768 bytes and 4,000 lines. Input retains the 4,000-line/120-character bounds. The native full-segment stack check and memory map belong only to this profile, not the IR contract. Explain implementation limits separately from virtual-machine semantics.

Verify unchanged IR sources in both a processor-independent semantic interpreter and the native backend. Deliberately use different data addresses and handle representations in the interpreter, comparing program status, byte output, and file effects. That interpreter is a verification tool only: it must never generate assembly or machine code or supply a bootstrap artifact. Keep runtime source, examples, accepted/rejected fixtures, archive contents, and documentation consistent. The initial RILL compiler must use this processor-independent language and portable service interface.

## 12. Initial RILL implementation

The first RILL compiler is written entirely in the published processor-independent IR86 language and emits IR86 source. Build it with the unchanged IR86 translator and ASM86. Its native image is 5,173 bytes, its assembly text is 24,676 bytes, and its 255 total definitions fit the existing target limits. No preparatory changes to the preceding tools or outside compiler are permitted.

The initial subset has one `fn main()`, twenty-six single-letter mutable word variables, unsigned decimal literal initializers, assignment, binary addition/subtraction, unary minus, parentheses, `if`/`else`, `while`, byte output/input, persistent service status, and explicit program exit. Arithmetic wraps as a sixteen-bit word; comparisons are unsigned. Relations occur only in control conditions. All declarations precede statements in the outer body. This implementation has no user-defined procedures, arrays, strings, type annotations, ownership checking, or self-hosting claim. Its limitations and their reasons must be explicit in the reference.

Use fixed work files SOURCE.RIL and RESULT.IR. Buffer the complete accepted IR and successfully close the source before creating the result. Source/input rejection preserves an older result; final output I/O failure may leave partial output. Report a line and category, return nonzero on failure, and use the unchanged CHECK.BAT for immediate visible PASS/FAIL. Keep byte-input program semantics separate from the compiler's Control-Z source convention.

Supply twenty-nine gradual construction checkpoints, a workbench, a complete pipeline exercise, language/compiler reference, and four complete programs. Early checkpoints are explicitly diagnostics. The first empty-program compiler is checkpoint fifteen. Preserve exact source edits and old context, distinct article descriptions, source-only ASCII/CRLF/8.3 downloads, and new collection illustrations. Keep workbench sources in pub_src/workbench/rill, publications in pub_src/site/content/bootstrap/rill and static/downloads/rill, and production evidence in pub_src/qa/rill.

Bound the input to 4096 bytes, generated IR to 1024 bytes, and saved compiler state to thirty-two words. BODY and FACTOR share an eight-level active parser bound. Keywords retain their complete spelling in two exact base-32 letter groups, not a lossy hash. Treat scratch-cell sharing and recursive saved state explicitly in the helper interfaces.

Verify every checkpoint through the actual IR86 and ASM86 executables. Execute complete compiler sources in both the independent IR semantic model and native backend, with differing data bases and opaque handle values, and compare unchanged source output. Verify emitted programs against the IR model and native execution. Prove the complete BASIC → ASM86 → IR86 → RILL → IR86 → ASM86 → program path, and separately check the compiler, examples, rejection preservation, and all byte values under DOS 3.10. An independent interpreter remains verification only and must not supply a bootstrap artifact.

## 13. ASM86A capacity-building stage

Use the concrete architecture and construction gates in [ASM86A_Design.md](ASM86A_Design.md). Insert ASM86A after ASM86 and before the expanded IR86. Do not rename ASM86, alter its published bootstrap capacity to make the new source fit, or use an outside assembler, linker, encoder, or prebuilt executable.

The first milestone, ASMA0, must fit ASM86's 8192-byte output, 256-symbol, 4000-line, and 120-character limits. It uses fixed files, sequential block input, streamed temporary output, two passes, and 2048 in-segment symbols. It adds the segment-MOV/ES-memory encoding forms needed to build the larger implementation while its own source remains in ASM86's language. Prove its direct build and self-assembly before using it as a builder.

The full ASM86A target has 8192 symbols with 31-character names, eight separately allocated 40 KiB symbol pages, a separate 8 KiB lookup-bucket block, 4 KiB input/output blocks, a bounded 1023-character physical line, and checked 32-bit source counters. Its main segment reserves a fixed code/data region, parser and file buffers, and a 4 KiB stack. Its explicit memory requirement is 392 KiB plus DOS allocation/environment overhead; reject memory shortage before touching output rather than assuming the reference machine has enough free RAM.

Both milestones may emit at most 61,184 bytes, occupying 0100H–EFFFH in the current `.COM` profile. Output is streamed, not held in the assembler's resident memory. Source and target sizes are independent. Keep source rejection from replacing an older successful result by publishing a closed temporary file through the documented rename/recovery protocol. Use SOURCE.ASM, RESULT.COM, ASMA.TMP, and RESULT.BAK without filename prompts.

Grow language support gradually: quoted data and known-size reserves/constants; segment access; 8086 addressing and frame-related forms; arithmetic/string operations; and explicit five-byte NEAR conditional expansions without generated skip symbols. Preserve fixed encoding sizes between passes and reject later-CPU encodings. Keep the first full assembler source within the seed's language; new accepted forms are not automatically available to its builder.

Only after ASM86A passes direct-build, self-assembly, capacity, failure-path, compatibility, and DOS 3.10 checks should the expanded IR86 and RILL depend on it. Those tools must separately remove their complete-output buffers and small symbol/parser limits. Define portable procedure, local-storage, indexed-data, and allocation interfaces before growing RILL; do not expose assembler segment conventions as IR or RILL semantics. The existing small RILL subset is not the intended ceiling for the language.


## 14. The RILL-written toolchain

The native streaming translator is IRWIDE.ASM. Its twenty-three buildable IW checkpoints start from the published ASM86A source and supply bounded streams, recoverable publication, word operations, procedures and local slots, literal strings, and opaque file/memory-block services. It is built by the unchanged native ASM86A. IR semantics never expose physical registers, flags, segments, interrupts, or DOS descriptors.

RILLBOOT.IR is the authored IR-written compiler seed, built through that native translator and assembler. Forty-seven RB checkpoints construct its helpers, complete-spelling scanner, initialized records, streamed emitter, expression parser, lexical scopes, procedures, and checked publication. The complete seed is identical to RB47.IR. No host-language translation produces this source.

RILL.RIL is the self-compiling compiler, identical to RC43.RIL. Forty-three RC checkpoints express it in the same published language. Source names are folded ASCII up to 24 characters; there are 512 global/procedure records, sixteen parameters, sixteen simultaneously live local words, thirty-two active local-name records, and bounded block/expression recursion. Source and output stream through 4096-byte blocks. Ordinary pointer/index access is unchecked; opaque allocated-block access is checked. Do not imply Rust ownership or memory safety.

IR86.RIL and ASM86A.RIL implement the translator/backend and the full streaming assembler. They use ordinary RILL features and portable services, without embedded project executables or private code-generation escapes. The assembler preserves 8192 complete-spelling symbols and the EF00H target image profile. Its encodings remain compatible with the published native assembler.

TMAKE.BAT builds the native bridge and IR-written compiler seed from a preserved ASMAKEEP.COM, then all three RILL implementations. It builds each tool twice more using only the preceding RILL-written compiler, translator, and assembler. Stop at the first nonzero status. Compare A0/A1/A2, I0/I1/I2, and R0/R1/R2 byte for byte; all corresponding files must match. A separate fresh bootstrap begins by executing canonical BOOTASM.BAS. Actual DOS 3.10 must execute the same reader batch and match every generation.

Keep workbench source and downloads in pub_src/workbench/toolchain and site/static/downloads/toolchain. The TOOLCHN.ZIP archive contains ASCII/CRLF/8.3 sources and no COM/EXE or historical interpreter. The static-site validator reconstructs all 113 continuation checkpoints from printed edits and checks complete port notebooks, fixtures, examples, archive bytes, links, and assets. The portable IR model is validation only and never supplies a bootstrap artifact.
