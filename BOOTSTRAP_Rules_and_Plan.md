# The Bootstrap Project: Rules and Plan

## 1. Purpose and status of this document

Build an understandable, hand-entered chain of tools, beginning with an assembler written in GW-BASIC and eventually reaching a self-hosted compiler, supporting utilities, a linker, libraries, and a small operating system.

Learning and independent construction are central goals. The reader should understand what they type, be able to test it in manageable stages, and retain a working tool at each major milestone. Short articles, modest typing requirements, and gradual progress are primary design concerns: a human will enter every required line.

This is a fresh start. Use this document and decisions made for this version of the project; do not use previous conversations to guide development.

Publish the articles as static HTML generated by Hugo. Keep all intermediate builds and source files in a directory named `pub_src`. Publish the generated website to `public` at the project root.

This file is the project plan, not a magazine article. It may discuss sequencing, future work, production procedures, and unresolved decisions. The articles themselves must follow the stricter editorial rules below.

### Bootstrap ladder

| Stage | Tool | Purpose and implementation |
|---|---|---|
| 1 | BOOTASM | An assembler written in GW-BASIC; the starting point for the toolchain. |
| 2 | ASM0 | An assembler written in assembly accepted by BOOTASM. It self-assembles and builds ASM1. |
| 3 | ASM1 | A streaming seed assembler built directly by unchanged ASM0, then self-assembled. It supplies the bounded streams and segment access needed to build ASM86. |
| 4 | ASM86 | A larger assembler constructed in ASM1, then self-assembled. Stream input and output, allocate substantial symbol storage, and provide the addressing/instruction support needed by larger tools. |
| 5 | IR86 | A processor-independent intermediate language and translator. The expanded implementation is built with ASM86 and emits ASM86-compatible 8086/8088 assembly. |
| 6 | RILL0 | A language with Rust-like syntax, without a commitment to Rust's full safety checking or other features. Its initial compiler is written in IR86; expand it using the capacity supplied by ASM86 and the expanded IR86. |
| 7 | RILLBOOT | Construct the expanded systems-language compiler in IR86, preserving RB12.IR as RILLBOOT.IR and its executable as RILLBOOT.COM. |
| 8 | RILL | Express that compiler in RILL through RC01–RC43, then prove its self-builds and the complete toolchain loop. |
| 9 | Rebuild in RILL | Reimplement the assemblers and later tools in RILL, working toward a self-hosted toolchain. |

Later work will cover a linker, libraries, larger programs, expanded language and assembler features, and a small operating system. Detailed scope and ordering remain to be decided.

The complete toolchain is implemented and verified. Unchanged ASM0 builds ASM1, which builds ASM86. The streaming native IR86 bridge builds the IR-written compiler seed; that seed builds RILL, and RILL builds the IR86 and ASM86 implementations. Both rebuild generations reproduce all three tools using only the RILL-written trio. The required native IR and initial compiler evolve through their constructions. See [TOOLCHAIN_Design.md](TOOLCHAIN_Design.md).

## 2. Non-negotiable editorial rules

- Write as an original hands-on programming magazine series with a **1986 technical horizon**, in the spirit of Dr. Dobb's Journal. Do not claim affiliation or pretend the articles are authentic historical publications.
- Present each collection as its first publication. Do not discuss revisions, previous drafts, AI-generated development, editorial corrections, or abandoned approaches in article prose.
- Acknowledge the BASIC series as the foundation of the assembly series. A brief prerequisite reference to an earlier published collection is appropriate; revision-history commentary is not.
- Keep article explanations self-contained. **Only introductions may acknowledge future goals.** The body should explain the program being constructed, without promises about a later compiler, operating system, or installment.
- Do not use checksums. Do not mention checksums or checksumming in articles, listing commentary, or reader-facing companion documentation.
- Do not mention modern development machinery in reader-facing material: Unicorn, Python harnesses, automated regression infrastructure, modern build verification, AI tools, or similar production details.
- Do not insert web addresses, online archives, or digital-transcription references into the period magazine narrative. Cite appropriate printed manuals by title, publisher, date, and relevant section when needed.
- Do not replace modern testing disclosures with invented claims of testing on period hardware. Give the reader reproducible DOS/GW-BASIC checks and expected results.
- Use clear, patient language suitable for a beginner. Explain unfamiliar terms where they are used.
- Do not announce how many source lines a listing, patch, or completed checkpoint contains in published prose. Keep typing-size budgets as internal authoring constraints. Retain line numbers needed to locate edits and source limits needed to explain program behavior.
- Keep real limitations explicit. Distinguish CPU capabilities from the smaller language our assembler accepts. Do not imply support for full C merely because the assembler can support a small compiler.
- Explain all limitations fully, including why each limitation was chosen.
- Use natural, concrete prose consistent with the 1986 setting. Avoid formulaic or AI-sounding language.
- Double-check all produced text and code for correctness.

## 5. Code and type-in rules

### Size and readability

- Keep articles and required type-in code short. Include the explanation needed for understanding, but defer features that would make a step too large.
- Build BOOTASM in logical, testable chunks of **no more than 50 required BASIC source lines per chunk**.
- Assembly sections may exceed 50 lines. Keep them as small as practical; organize by a coherent routine or capability rather than an arbitrary page break.
- Treat line counts as a ceiling, not a target. Do not pack long statements or several unrelated operations onto a line merely to meet the limit.
- Favor beginner-readable code while economizing on lines people must type. Avoid unnecessary scaffolding, repetitive instructions, and needless register reloads.
- Silently apply straightforward instruction economy. Do not add prose congratulating the implementation for eliminating redundant reloads.
- Do not trade understandable control flow for obscure tricks simply to save a few lines.
- There is no fixed limit on convenience features. Include them only when their benefit justifies the added typing, explanation, and implementation complexity.

### Gradual progression

- Add one small, coherent capability at a time, with a working and visibly testable stopping point before the next addition.
- Introduce prerequisites before relying on them. Do not make large jumps merely to reach the next named tool sooner.
- Spread each tool's construction across as many installments and checkpoints as needed. The tool sequence describes milestones, not the size of individual steps.
- Account for the reader's total typing burden, including source changes, replacement blocks, helpers, and test input. Avoid repeated retyping of large sections.
- If a proposed step's size or conceptual jump is uncertain, ask the user about pacing before committing to it.

### Minimum scope for every handoff

- Keep every bootstrap tool as small and simple as required to construct the next stage. Before adding a feature, name its concrete successor source, construction checkpoint, runtime binding, or required self-build that uses it.
- Count the entire reader burden: new concepts, typed source, replacements, scaffolding, and tests. Minimum scope does not mean compressed code or obscure tricks.
- A larger accepted language can be implemented using a smaller predecessor language. Do not teach the predecessor an operation merely because the successor will accept or emit it.
- Introduce capabilities when the next consumer actually requires them. General-purpose completeness, convenient examples, and unspecified future tools do not justify extra bootstrap features.
- Retain correctness: checked bounds, useful errors, required DOS status, source-error preservation, and the established recovery contract are part of a working tool. Keep tests focused on its actual output, using file length and byte inspection when there is no retained display behavior.
- Allow practical, explained capacity headroom. Tightening a constant is not an improvement if it saves no implementation complexity and makes human construction brittle.
- Keep the first IR86 translator and RILL0 required. Their implementations must evolve into streaming IR86 and RILLBOOT through complete, working, modest changes. Do not substitute independent replacements or leave the earlier tools as unused demonstrations. Preserve established behavior at each migration checkpoint, with explicit compatibility tests.
- A successful self-build proves reproducibility, not minimal scope or source continuity. Do not certify a stage as minimal until those separate checks pass.

### Bootstrap integrity

- Every stage must be buildable with a tool the reader already has.
- Start with GW-BASIC and the DOS workbench, then build each tool using the preceding tools in this project. No outside assembler, compiler, linker, code generator, or prebuilt project executable may supply any part of the bootstrap chain.
- Keep IR language semantics independent of CPU and OS conventions; put those conventions in the backend and runtime binding.
- Build the first ASM0 executable with BOOTASM. Build ASM1 directly with the unchanged ASM0, then ASM86 with ASM1. Build the expanded IR86 with ASM86, and RILL with IR86 and ASM86. Preserve the existing baseline chain while constructing the inserted stage.
- Target DOS `.COM` executables only for now. Keep near code, ordinary data, and stack in the main segment; permit explicitly DOS-allocated auxiliary workspace selected through ES for larger tools. This workspace does not expand a `.COM` file's near-code/image limit or introduce an `.EXE` format. Defer multisegment code, linking, and other executable formats.
- Fixed input/output filenames are acceptable for early tools. Use COPY to select source files; filename prompts and command-line parsing are not prerequisites. Expanded tools should stream files through bounded blocks rather than buffer their complete input or output.
- Clearly distinguish the language used to **implement** an assembler from the assembly language it **accepts** and the machine code it **emits**.
- Do not silently use a new instruction in the assembler's own source before the preceding assembler can assemble it.
- Preserve a known working bootstrap executable under a separate name.
- Keep symbol-table bounds, source limits, memory use, stack requirements, and short-branch reach explicit.
- Do not quietly adopt 80186/286/386 instructions merely because the user's emulated machine can execute them. The established instruction baseline is 8086/8088.

### Listing presentation

- Show exact insertion points, enough surrounding code to locate them, and complete replacement blocks. Avoid vague directions such as “change the parser accordingly.”
- Make it unambiguous whether a block is new source, replacement source, a command, or an example.
- Printed margin numbers must be clearly separate from actual source. BASIC line numbers are source and must be typed.
- Explain inputs, outputs, scratch variables or registers, preserved state, and important side effects for each substantial routine.
- Explain data representation, instruction encoding, and branch calculations alongside the relevant addition.
- Preserve ASCII source, DOS-compatible line endings, and practical 8.3 source filenames for the period workbench.

## 6. Required structure of an installment

Each construction installment must contain:

1. A concrete objective and a short explanation of the problem it solves.
2. An explanation of why this part is needed at this point in the construction, grounded in the current program and its prerequisites.
3. The necessary concepts, introduced at the point of use.
4. Exact source additions and replacements.
5. Detailed explanations of each addition, including interactions with existing routines.
6. A stopping point that can be assembled or run with tools already available.
7. Exact test input, commands, and expected output or machine bytes, following the checkpoint rules below.
8. At least one relevant rejection or boundary case when the new behavior warrants it.
9. Brief troubleshooting advice tied to likely mistakes.

### Checkpoint rules

- Every checkpoint must give the reader a visible result wherever practical: console text, a displayed value, or a named output file with exact inspection instructions and expected contents.
- If a test communicates only through DOS exit status, print a small batch check that reports both PASS and FAIL; do not treat a silent return to the prompt as evidence of success. Check the status immediately, before launching any other program.
- Expected rejection tests must visibly distinguish the expected failure from unexpected acceptance. State the exact diagnostic or status and how to observe it.
- Binary viewers must display the file length as well as bytes, so a valid empty output is visibly distinguishable from no result.
- Never execute a fixture intended only to test instruction encoding; inspect its emitted bytes instead.
- Prefer existing console reports, `TYPE`, a small `VIEW.BAS`-style viewer, or a shared `CHECK.BAT` helper over adding substantial test machinery to the compiler itself.

## 10. ASM0 construction scope

ASM0 begins with a short DOS message program, then adds decimal reporting, errors, filename input, file handles, byte reading, physical lines, tokens, lookup tables, values, output buffering, data directives, two passes, registers, labels, and instruction families. Twenty-nine buildable source checkpoints precede a thirtieth installment that compares two native self-assembly generations with the BASIC-produced original. A workbench guide, a complete reference, and three short executable examples accompany them. Keep new collection artwork distinct from BOOTASM's.

The completed BOOTASM.BAS must directly assemble every ASM0 construction source, including the final native assembler, without a preparatory patch or alternate assembler variant. Give BOOTASM a 256-entry symbol table, a 4,096-byte output limit, and a 2,000-line source limit; all ASM0 construction sources must fit those bounds and use only its accepted instructions. The final native image is 2,574 bytes. Keep each assembly addition coherent and modest enough to type. Printed edits identify exact old context and are applied from the bottom upward to preserve physical line locators.

Keep ASM0 workbench sources in `pub_src/workbench/asm86`, source downloads beneath `pub_src/site/static/downloads/asm86`, and verification evidence in `pub_src/qa/asm86`. Reader executable bytes must come from executing the published BASIC or native assemblers.

## 11. IR86 language, backend, and runtime

IR86 is a processor-independent virtual machine with accumulator A, explicitly defined sixteen-bit word semantics, an expression stack, byte-addressed declared storage, procedure parameters and local slots. Its language must not expose physical registers, flags, segments, interrupts, operating-system service numbers, or native descriptor values. Canonical low-byte-first words are virtual-machine semantics; another backend must preserve them.

There is one native translator construction. IR01 through IR23 reuse the bounded reader/publication routines, then grow the first text translator through storage, expressions, branches, frames, strings, files and checked allocated workspace. Every source is built with ASM86. IR86.ASM, IRWIDE.ASM and the final checkpoint are identical; IRKEEP and IWKEEP are retained executable aliases. There is no separate translator restart after the initial construction.

Use fixed SOURCE.IR and RESULT.ASM with recoverable temporary/backup publication. Stream 4096-byte blocks, bound a physical line to 1023 characters, and use checked two-word source/output counters. Let ASM86 supply label resolution, symbols and the 61184-byte COM image bound. Explain these target-profile limits separately from IR semantics.

Accept only the operation vocabulary used by the compiler constructions or their generated tool sources. PUTC, STATUS, opaque file handles, counted READ/WRITE, publication services, allocated blocks and checked block access are required. Console byte input, signed comparisons, redundant declaration/store forms and unused opcode aliases are outside this native vocabulary. Every accepted operation must have a successor-source witness.

The language reference describes operand classes, stack actions, frames, canonical word storage and normalized service status. Preserve complete source edits, meaningful acceptance checks and output preservation on rejection. Verify unchanged IR in the native backend and an independent semantic model with different data addresses and handle representations. The model is verification only; it never supplies a bootstrap artifact.

## 12. Initial RILL implementation and continuation

RILL0 is written in IR86 and emits IR86. Build every saved compiler source with the native IR86 and ASM86 tools. Its first language has one argument-free fn main(), complete folded identifiers, mutable local words, + and -, unsigned comparison values, parentheses, assignments, lexical blocks, if/else, while, putc, status, exit and return. Omit strings, globals, user procedures, multiply/divide and unused intrinsic wrappers until their construction stages.

Use the same scanner, initialized 40-byte symbol records, local binding layout, streamed emitter, parser state and recoverable file publication in RILL0 and RILLBOOT. Construct these helpers gradually in R01 through R39. Preserve R39.IR as RILL0.IR (internal production alias RILL.IR). RILLBOOT begins by editing that exact accepted source; every RB checkpoint remains a complete compiler for the preceding subset.

RB01 through RB12 add unsigned products/quotients/remainders; masks, right shift and logical negation; strings and byte loads; global words; byte buffers; named procedures; parameters and recursion; counted files; publication services; allocated workspace; and checked block access. The completed seed accepts only syntax used by RILL.RIL and its construction checkpoints. It omits XOR, left shift, unary minus, bitwise complement, explicit address-of, getc, load16, store8 and store16. The RILL-written compiler can add the operators and pointer wrappers required by the later tool sources.

Keep fixed SOURCE.RIL and RESULT.IR. Stream through RILL.TMP and RILL.BAK; source rejection preserves the prior result and publication failure retains recovery options. Both compiler milestones use 4096-byte blocks, checked two-word diagnostics/output counts, 24-character folded names, sixteen active expression/block levels and sixteen live local slots. The shared table layout reserves 512 global/procedure records and 32 local records in a 22000-byte opaque block; capacity headroom does not require extra grammar or a different implementation.

Use natural compiler reports and retained output files as acceptance evidence. Inspect exact fragment lengths and bytes with VIEW.BAS. Pure runtime helpers may compare their result and return status through CHECK.BAT. Do not add disposable display scaffolding or repeat unrelated predecessor failures in every lesson. Verify each continuation still accepts the earlier complete language, then prove the seed builds the RILL compiler and the compiler builds the remaining tools.

## 13. ASM1 and ASM86 capacity-building stages

Use the concrete architecture and construction gates in [ASM86A_Design.md](ASM86A_Design.md). Place ASM1 after ASM0, then ASM86 before the expanded IR86. Publish ASM1 and ASM86 as separate sibling collections: twelve seed construction articles and twenty-four larger-assembler articles, each with its own workbench, reference, complete programs, and source archive. Keep the established A01–A40 disk filenames and preserve links to the seed articles at their earlier addresses. Restart ASM86 chapter numbering at 01; its first source remains A13.ASM, copied from verified ASM1.ASM. Shared source construction and shared checkpoint verification may remain together under pub_src/tools and pub_src/qa/asm86a. Do not rename ASM0, alter its published bootstrap capacity to make the new source fit, or use an outside assembler, linker, encoder, or prebuilt executable.

The first milestone, ASM1, must fit ASM0's 8192-byte output, 256-symbol, 4000-line, and 120-character limits. It uses fixed files, sequential block input, streamed temporary output, two passes, and 2048 in-segment symbols. It adds the segment-MOV/ES-memory encoding forms needed to build the larger implementation while its own source remains in ASM0's language. Prove its direct build and self-assembly before using it as a builder.

The full ASM86 target has 8192 symbols with 31-character names, eight separately allocated 40 KiB symbol pages, a separate 8 KiB lookup-bucket block, 4 KiB input/output blocks, a bounded 1023-character physical line, and checked 32-bit source counters. Its main segment reserves a fixed code/data region, parser and file buffers, and a 4 KiB stack. Its explicit memory requirement is 392 KiB plus DOS allocation/environment overhead; reject memory shortage before touching output rather than assuming the reference machine has enough free RAM.

Both milestones may emit at most 61,184 bytes, occupying 0100H–EFFFH in the current `.COM` profile. Output is streamed, not held in the assembler's resident memory. Source and target sizes are independent. Keep source rejection from replacing an older successful result by publishing a closed temporary file through the documented rename/recovery protocol. Use SOURCE.ASM, RESULT.COM, ASMA.TMP, and RESULT.BAK without filename prompts.

Grow language support gradually: quoted data and known-size reserves/constants; segment access; 8086 addressing and frame-related forms; arithmetic/string operations; and explicit five-byte NEAR conditional expansions without generated skip symbols. Preserve fixed encoding sizes between passes and reject later-CPU encodings. Keep the first full assembler source within the seed's language; new accepted forms are not automatically available to its builder.

Only after ASM86 passes direct-build, self-assembly, capacity, failure-path, compatibility, and DOS 3.10 checks should the expanded IR86 and RILL depend on it. Those tools must separately remove their complete-output buffers and small symbol/parser limits. Define portable procedure, local-storage, indexed-data, and allocation interfaces before growing RILL; do not expose assembler segment conventions as IR or RILL semantics. The existing small RILL subset is not the intended ceiling for the language.


## 14. The RILL-written toolchain

The native streaming translator is IR86.ASM, with identical retained IRWIDE.ASM and IRKEEP/IWKEEP executable aliases. Its single construction grows the initial text translator into the complete compiler builder. There is no second native translator implementation.

RILLBOOT.IR is the final RB12 source, grown from the accepted RILL0 source. It builds RILL.RIL; the resulting R0 compiler builds the translator and assembler ports.

RILL.RIL is the self-compiling compiler, identical to RC43.RIL. Forty-three RILL checkpoints express it in the same published language. Source names are folded ASCII up to 24 characters; there are 512 global/procedure records, sixteen parameters, sixteen simultaneously live local words, thirty-two active local-name records, and bounded block/expression recursion. Source and output stream through 4096-byte blocks. Ordinary pointer/index access is unchecked; opaque allocated-block access is checked. Do not imply Rust ownership or memory safety.

IR86.RIL and ASM86.RIL implement the translator/backend and the full streaming assembler. They use ordinary RILL features and portable services, without embedded project executables or private code-generation escapes. The assembler preserves 8192 complete-spelling symbols and the EF00H target image profile. Its encodings remain compatible with the published native assembler.

TMAKE.BAT builds the native bridge and IR-written compiler seed from a preserved ASMAKEEP.COM, then all three RILL implementations. It builds each tool twice more using only the preceding RILL-written compiler, translator, and assembler. Stop at the first nonzero status. Compare A0/A1/A2, I0/I1/I2, and R0/R1/R2 byte for byte; all corresponding files must match. A separate fresh bootstrap begins by executing canonical BOOTASM.BAS. Actual DOS 3.10 must execute the same reader batch and match every generation.

Keep workbench source and downloads in pub_src/workbench/toolchain and site/static/downloads/toolchain. The TOOLCHN.ZIP archive contains ASCII/CRLF/8.3 sources and no COM/EXE or historical interpreter. The static-site validator reconstructs all 113 continuation checkpoints from printed edits and checks complete port notebooks, fixtures, examples, archive bytes, links, and assets. The portable IR model is validation only and never supplies a bootstrap artifact.
